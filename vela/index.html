Vela: a sub-microsecond verifiable spot DEX matching engine

On making the fastest published verifiable matching engine, and what it took.

August 2026 Live · GitHub · Docs

01 Context

Centralised exchanges have won on latency and won on UX. Every serious DEX in the last two years has been an attempt to close that gap without giving up the property that made DeFi worth building in the first place: anyone can verify what the exchange did. The interesting design question is no longer “can a DEX match at CEX speed” — Pulse proved you can, in Rust, on a laptop. The question is how far you can push the matcher while keeping every match cryptographically pinned to state a user can audit.

Vela is our attempt at that. It is a Rust central limit order book that runs each market as an independently locked shard, produces a state root every batch, anchors those roots on Ethereum every ten minutes, and settles withdrawals through an operator‑signed smart contract with a seven‑day emergency exit. The engine matches at 0.38 μs p50 and sustains 2.5M orders/sec in isolation. The end‑to‑end HTTP+WebSocket path — signature verification, JSON serialisation, WAL fsync, DA submission — closes at 16.9 ms p50 over 127.0.0.1 loopback on an Apple M3.

None of that is the point on its own. The point is that every one of those matches is deterministic, replayable from the write‑ahead log, hashed into a Merkle root, and posted on a public chain. If we ever lie about what happened, anyone with the log can prove it. This piece is a walk through how the pieces fit together, what we changed to get the numbers where they are, and what we deliberately left for later.

02 Benchmarks

Two sets of numbers, because they measure different things and conflating them is how every “fastest DEX” benchmark gets rightly torn apart.

03 Architecture

Vela is an eight‑crate Cargo workspace. The split follows lock granularity: everything that has to be mutated on the hot path lives in engine, everything that touches disk or the network lives in api, everything cryptographic lives in a crate of its own. The dependency graph is a straight line from types out to the wire.

Everything from the browser to the Ethereum settlement layer transits through a single Axum process. There is no separate matching service, no separate WebSocket gateway, no sidecar. This is a deliberate constraint — inter‑process messaging is where every DEX I've profiled bleeds tens of microseconds. Colocating the matcher, the WAL, and the response fan‑out keeps the entire hot path inside one address space and one lock hierarchy.

04 State

All exchange state — balances, resting orders, user metadata (nonce windows, open order IDs, credit ratios, quoted notional) — lives in a depth‑32 sparse Merkle tree in memory. Every mutation flows through a StateCache that mirrors writes into the SMT, so producing a root at commit time is O(dirty × 32), not O(state).

Durability is a combination of two things. Every sixty seconds we snapshot the entire engine to a JSON file on the Fly volume, and on every order we append a WAL entry — ORDER_POST, ORDER_PROCESSED, one FILL_CREATED per fill — with a single amortised sync_all per batch. On restart the process loads the newest snapshot and replays the WAL from the last checkpoint to reconstruct the exact pre‑crash state. Clean shutdowns write a clean_shutdown: true marker into the final snapshot so recovery can distinguish a graceful exit from a crash and skip replay.

The choice of a sparse Merkle tree over a Merkle Patricia trie is deliberate. The MPT is what Ethereum uses because it needs prefix‑compressed keys for RLP‑encoded account addresses. Our keys are already 32‑byte hashes of structured state — no path compression buys us anything, and the fixed‑depth SMT gives us O(1) proof size and cheaper delta computation.

05 Matching engine

Each market has its own OrderBook. Bids and asks are two BTreeMap<Price, PriceLevel>, each level a VecDeque<Order> preserving arrival order. Best bid is bids.keys().next_back(); best ask is asks.keys().next(); both are O(log n).

The matching loop is price‑time priority. A taker walks matchable price levels using an iterator that yields references directly into the book:

let matchable_iter: Box<dyn Iterator<Item = (u64, &VecDeque<Order>)>> =
    match order.side {
        OrderSide::Bid => Box::new(book.matchable_asks_ref(order.price)),
        OrderSide::Ask => Box::new(book.matchable_bids_ref(order.price)),
    };

The _ref in the method name is doing a lot of work. An earlier version of this code cloned the matching levels into a Vec<(Price, Vec<Order>)> so it could iterate without holding the book borrow. That single allocation was 30% of the wall‑clock cost of a match on the 98%‑cancel benchmark. Switching to a borrowing iterator was the biggest single‑commit throughput win we've landed.

Four order types are supported. GTC rests. Post‑Only rejects if it would cross. IOC matches what it can and cancels the rest. FOK either matches in full or reverts every state change it touched. FOK atomicity is why the engine matches through a DeltaBuffer — a copy‑on‑write overlay that buffers balance mutations, metadata mutations, and order‑book operations. On success we call delta.commit(engine) and every buffered write applies. On rejection we delta.rollback() and drop the buffer — the underlying state is untouched. Measured cost of a full FOK rollback is 841 ns.

Nonce validation happens against a fixed‑size ring buffer of the last twenty accepted nonces per user. Twenty is not arbitrary — it's the maximum number of in‑flight orders we let a market maker have before requiring an ack, and it lets makers pipeline order submission without blocking on network round‑trips. Nonces are accepted if strictly greater than the smallest active nonce, or if the window isn't full yet. Storing them as a fixed [u64; 20] instead of the original BTreeSet<u64> cut per‑order metadata clone cost from 200 ns to 58.2 ns.

06 Sharded dispatch

Everything above describes a single‑market matcher. The engine as it runs in production is sharded: each market gets its own MatchingEngine instance behind its own tokio mutex, and the batch dispatcher hands orders out to shards in parallel. Because user state (balances, nonces, credit) is shared across markets, this needs a protocol.

The protocol has three phases per batch:

  1. Phase 1 — single write lock on UserState. Apply deposits and withdrawals directly. Snapshot balances and metadata. Validate every incoming order against the snapshot, tracking in‑batch reservations so a user can't double‑spend across markets. Allocate globally‑unique order IDs. Do not mutate nonces or lock balances yet — those are the shard's job. Release the write lock.
  2. Phase 2 — per‑market shard locks acquired concurrently via join_all. Each shard receives the snapshot as its DeltaBuffer base and processes orders against it. Nonces are accepted here; balances are locked here. Shards run in parallel and don't coordinate.
  3. Phase 3 — single write lock on UserState again. Fold each shard's final balance, metadata, and fee deltas back into the shared state.

The subtle bug we caught late in this design was in the fold. The original code did current.nonce_window = final_m.nonce_window.clone() — whichever shard was applied last silently overwrote the nonce windows accepted by earlier shards. Under the sharded engine, replay protection was order‑dependent. The fix was to merge the windows via union with the same eviction policy as accept() — union all shards, keep the newest NONCE_WINDOW_SIZE. Three property tests now cover the distinct/duplicate/overflow cases.

07 API handler

Axum on tokio, with a batch dispatcher sitting between the HTTP handlers and the shard engines. The dispatcher opens a window on the first incoming order and closes it at the earlier of 500 μs elapsed or 256 orders accumulated. Both bounds are env‑configurable (VELA_BATCH_WINDOW_US, VELA_BATCH_MAX_SIZE). Everything the window closes gets shipped to MarketShards::dispatch_sharded_batch as a single logical unit — one mutex acquisition, one commit, one WAL flush.

Each order request returns a one‑shot channel receiver. If the shard engine wedges — panic, deadlock, GC pause on the state RwLock — the receiver is wrapped in tokio::time::timeout with a 500 ms default (VELA_DISPATCH_TIMEOUT_MS) and the client gets a 504 rather than an indefinite hang.

WebSocket is the primary transport for live traders. Four channel types: orderbook:{market}, trades:{market}, markets, and per‑user authenticated account:{address}. Every envelope carries a per‑channel sequence number so a client can detect a gap after reconnection and re‑request from the last known seq. The public order‑book broadcast task copies raw (price, qty) tuples out from under the engine mutex, releases the lock, and does JSON serialisation outside — earlier versions held the lock across serde_json::json! for every subscribed market on every tick, pinning it across hundreds of allocations per iteration.

Observability is a hand‑rolled /metrics endpoint emitting Prometheus text format 0.0.4. Nothing exotic — orders/sec, batch dispatch latency, WS client count, feed drops, order‑channel send failures, last snapshot timestamp. A scrape‑side aggregator can compute percentiles from the drainable batch‑size histogram.

08 Committer

Every batch produces a CommitBatch: a snapshot of balances and metadata at commit time, the list of requests, and a keccak256 of all fill IDs in the batch. The committer writes this to a durable log and hands the state root off to the anchor task, which posts it on Ethereum every ten minutes.

The committer is also the place forced‑inclusion requests get injected. A user who thinks the operator is censoring their orders can call the /force-include endpoint (production will verify an L1 Merkle proof; the beta gates on an admin token). Force‑included requests get prepended to the next batch after a configurable timeout, bypassing the normal dispatch path entirely.

09 zkVM

Vela ships with an optimistic‑ZK settlement model, not full ZK per batch. Generating a STARK or SNARK proof over a matching‑engine STF at 2.5M ops/sec is four to six orders of magnitude too slow with today's provers. What we do instead:

  1. Every batch is assumed valid on submission.
  2. The state root goes on chain within ten minutes.
  3. Any user can download the batch, re‑execute it locally, and if the derived root doesn't match the on‑chain root, submit a fraud proof within a seven‑day challenge window.
  4. A validated fraud proof reverts the batch and slashes the operator.

This is the same optimistic model that made Arbitrum tenable when full ZK was infeasible for general‑purpose EVM. The Vela zkVM crate today ships with a PlaceholderProver that produces a deterministic tag rather than a real proof; the interfaces are in place for the day fast provers make full ZK practical.

10 Interesting features

Market-maker credit system

Traditional DEXs require full escrow: to quote 100 ETH of bids across a market, you have to have 100 ETH in the contract, locked and unusable for anything else. That's a deal‑breaker for professional market making, and it's the single most‑cited reason serious flow lives on CEXs. Vela lets a maker quote beyond their deposit up to a per‑user credit ratio (default 5×, tunable per address). Quoted notional is tracked in UserMetadata.total_quoted_notional and enforced on every post‑order.

What happens when a maker breaches their ratio — usually because a fill drained available collateral, or because their credit ratio was revised down — is more interesting than the ratio itself. Rather than reject the incoming order and leave the book stale, the engine walks the maker's open orders in arrival order and cancels the oldest until they're back inside their limit. Same maker keeps the same tightest quotes; only their deepest, oldest quotes get pruned.

Adverse-selection toxicity scoring

Every taker fill is scored on the hot path in the closed interval [0.0, 1.0]. The score combines three signals: an order‑flow‑imbalance accumulator maintained in a fixed‑size ring buffer, the depth the taker walks into the book, and the taker's size relative to the maker's quoted liquidity at that level. The scorer uses interior mutability (RefCell<ToxicityScorer>) so it can update per fill without needing a &mut self from the matching loop.

Fills with a score above the configured threshold trigger a temporary credit penalty on the affected maker — the same maker keeps their spread but their effective credit ratio drops for the penalty duration. The score is also broadcast on an authenticated ws://.../feed/toxicity WebSocket channel so makers can react to a run of toxic fills before the penalty even lands. Hot‑path overhead is under 50 ns at p50, kept there by allocating the OFI ring on shard construction and updating it in place.

Threshold-encrypted order book

The most interesting thing on the roadmap — and the thing that's in the committee crate today as a working prototype — is a threshold‑encrypted order book. Orders arrive as ciphertexts encrypted to a committee public key; a threshold of committee nodes runs partial decryption; the plaintext order is only revealed once t‑of‑n shares are combined. Every decryption produces a public proof, which gets committed alongside the batch.

The property this buys is frontrunning resistance at the sequencing layer. The operator can't peek at pending orders, can't reorder them by observed content, can't sandwich a large taker. The current implementation is HMAC‑SHA256‑based (a placeholder for full BLS threshold signatures) and the committee is single‑party, so this is scaffolding for a real threshold scheme, not the real thing. But the pipeline — ciphertext arrival, pending queue, partial‑decrypt request, threshold combine, proof recording — is fully wired.

HFT nonce ring buffer

The rolling twenty‑nonce window discussed under the matching engine is what makes maker pipelining feasible. A traditional strict‑increment nonce lets a maker have exactly one in‑flight order per account; a naive rolling‑set nonce is O(n) per accept. The fixed [u64; 20] is O(20) worst case, and because 20 is small enough to fit in a couple of cache lines the constant is trivial.

Copy-on-write delta buffer

Mentioned in passing under matching; worth calling out on its own. The DeltaBuffer is the reason we can offer FOK. Every mutation an order might perform — balance debit, balance lock, metadata update, order insert, order remove, partial fill — buffers into the delta. If the order matches in full, commit() replays the buffered writes into the engine. If it rejects, rollback() discards the buffer. State corruption in the middle of a partially‑applied FOK is not representable.

11 Optimisations

The path from “works” to sub‑microsecond p50 was mostly a sequence of surgical changes, each measured before and after. The high‑signal ones:

Optimisations landed, in order of impact
ChangeBeforeAfter
Zero-allocation matchable-level iteration Vec<(Price, Vec<Order>)> per match Borrowing iterator, no alloc
NonceWindow: BTreeSet → fixed [u64; 20] user_metadata_clone: 200 ns 58.2 ns (−71%)
Sharded matching (per-market lock) single engine mutex N shards, concurrent execution
ahash + mimalloc stdlib HashMap + system malloc 2-3× faster hashing on small keys
WAL fsync amortisation 1 fsync per WAL entry (3-5 per order) 1 fsync per dispatch batch
WS lock-hold reduction engine lock across JSON serialisation lock only for raw tuple copy
Release profile: fat LTO, panic=abort default codegen-units, panic=unwind smaller binary, tighter hot loops

The two most instructive of these are worth expanding.

Zero-allocation matchable iteration

The first version of the matcher pulled matching price levels out of the book into an owned Vec<(Price, Vec<Order>)> — one allocation for the outer vec, one clone per level for the inner. On the 98%‑cancel workload almost every taker call matched at most one level, but the allocation happened every time regardless. Adding matchable_asks_ref and matchable_bids_ref — iterators that yield (Price, &VecDeque<Order>) pairs by reference into the underlying BTreeMap — moved the whole match into the borrow region and dropped that allocation to zero.

A secondary bug hidden by the old code came out in the same commit: a resting order that had been partially filled before the current dispatch was being compared against its original quantity when checking full consumption. Any partial‑fill‑before‑dispatch scenario would fail to remove the resting order after a fill that consumed the remaining portion. The switch to borrowing iteration made the code path shorter, which made the bug legible enough to notice.

Sharded matching

The single‑mutex matcher scales linearly with active markets — sixteen markets doing 100k ops/sec each contend on the same lock. The sharded matcher runs each market on its own lock and lets the sixteen shards make progress concurrently, with the three‑phase protocol described earlier holding the shared user state coherent. The 2.5M ops/sec figure in Tier 1 is achievable specifically because the ten‑market benchmark can dispatch across ten shards without lock contention.

12 Extensions

What's deliberately not yet real:

  • Real threshold cryptography in the committee. The current TEOB pipeline uses HMAC‑SHA256 placeholders for what should be BLS threshold signatures. The interfaces and the pending‑order queue are production‑ready; the crypto is not.
  • Real TEE attestation. tee ships a PlaceholderAttester. The consumer of an attestation record verifies its shape, not its cryptographic authenticity. Wiring AMD SEV‑SNP attestation into the request path is well‑defined work; we haven't done it.
  • Real ZK proofs. Same shape as the TEE story — the crate exists, the placeholder produces deterministic tags, the pipeline handles proofs correctly when they arrive. What's missing is a fast‑enough prover.
  • Full consensus layer. Vela today is a single operator + fraud proofs. A production version wants HyperBFT‑style validator consensus so a single machine failure doesn't take the exchange offline. This is a large piece of work and the honest reason we haven't started it is that we're prioritising audit and mainnet deployment first.
  • Smart contract audit and mainnet deployment. Sepolia only, for now. A recent security pass caught a fund‑at‑risk bug in the withdrawal signature scheme (replay after redeposit) and it's fixed and fuzz‑tested — but the contract has not been through an external audit and shouldn't hold real funds until it is.

13 FAQ

How is 2.5M ops/sec possible when Pulse gets 125k with the same methodology?
Three things stack. First, sharded per‑market execution — Pulse serialises through one matcher. Second, zero‑allocation matching iteration where Pulse still clones matching levels. Third, an ahash + mimalloc combination that's worth 5–15% on the HashMap‑heavy hot path. The M3 is also faster than the M2 Pro on single‑core integer work, which accounts for some but not most of the gap.
What happens if the operator (that's us) goes down?
Two things. In the short term, the engine restarts from its latest snapshot plus WAL replay, so no accepted orders are lost. In the long term, any user can invoke initiateEmergencyExit on the settlement contract, wait seven days, and then executeEmergencyExit to withdraw their deposited funds directly — no operator signature required. Deposited funds are never in operator custody.
What stops the operator from censoring specific users?
The /force-include endpoint. In production this verifies an L1 Merkle proof that the request was submitted to a delayed inbox on Ethereum. Once submitted there, the request is guaranteed to be included in the next batch after a configurable timeout, or the operator can be slashed via fraud proof.
What stops the operator from stealing funds?
The settlement contract only lets the operator sign withdrawals. Every withdrawal requires an operator signature and matches the operator's off‑chain accounting via a state‑root fraud‑proof mechanism. The operator can sign more than a user is owed, but a fraud proof against the resulting state root will slash them. The recent contract security pass fixed a signature‑replay bug in this scheme — the withdraw hash now includes address(this) to prevent cross‑contract replay and consumes the nonce to prevent same‑contract replay.
Why not full ZK from day one?
Prover throughput. Producing a SNARK per batch at 2.5M ops/sec is 10⁵–10⁶× too slow with today's general‑purpose provers. The optimistic model gets us 95% of the security property (the 5% being time‑to‑finality) at 0% of the prover cost. When per‑batch STARK proving gets fast enough, the zkVM crate's ZkProver trait is where we swap in the real implementation.
How much state can the engine actually hold?
Bounded per‑market via OrderBook::max_orders. On the current Fly VM (2 vCPU, 2 GB) we can comfortably hold 10k orders per market across all sixteen markets while retaining the p50 numbers reported here. Serialised snapshots are ~1 MB at that load. Scaling to more state means either a larger VM, sharding markets across processes, or off‑loading historical order data to durable storage while keeping only the live book in memory.
